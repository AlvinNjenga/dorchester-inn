# Shared UI

`CatalogueGrid` optionally accepts `columns={4}` for four columns from 1024px; the amenities example uses this. Default room/service grids remain three columns. Mobile/tablet stay at one/two columns.

Place reusable UI components here. Components receive data through props rather than owning route definitions or WordPress requests.

`ServiceDetailLayout` consumes `ServiceDetail` (the catalogue Service plus optional paragraphs) and an optional supplied contact action using `to` or `href`. It renders one H1/breadcrumb band, a dimensioned 4:3 photo or explicit development placeholder, description/prose, practical information when nonempty and a contact section only when an action exists. It owns section containers/spacing and requires a full-width route handle. It does not fetch data or own business contact facts. Development-only `/__service-sample/:sampleSlug` previews cover Lounge, Massage Chair, a clearly labelled long-content/image fixture, and omitted optional fields. Actual service pages remain assigned to Epic 6.

`ContactTile` receives an icon key (`phone`, `email`, `address`), title, selectable text value and optional `{ label, href }` or `{ label, to }` action. It renders a labelled article with a decorative icon and H3 (optional H2). Only the explicit action is clickable; the value remains copyable. It owns neither business data nor map destinations. The style sample uses shared phone/email/address data, with the address informational until a map is verified.

`AmenityTile` consumes a typed amenity label and icon key from `content/catalogue.ts`. It renders a decorative, assistive-technology-hidden Lucide icon above visible text. Tiles are informational, with no link/button role, pointer cursor or tab stop. They wrap naturally and compose within CatalogueGrid. The development page shows private rooms, in-house bar, restaurant and included lounge access; no unsupported facilities or pricing claims are added.

`ServiceCard` consumes a typed `Service`. It uses a portrait 3:4 photo area with a white title panel, followed by visible description/practical details and one gold destination link. Photos are optional while owner assets are pending; the fallback explicitly identifies a development placeholder. No hover is needed to read essential information. The heading defaults to H3 (optional H2), labels its article with an instance-unique ID, and wraps naturally. Empty practical-detail arrays omit the list. Lounge/Massage Chair/Our bar examples use `serviceCatalogue` in the development sample; no guessed price or happy-hour schedule is added.

`RoomCard` consumes a typed `Room` with a source-mapped image, title, description and fixed USD/KES nightly prices. It uses an article labelled by an instance-unique heading, default H3 (optional H2), a dimensioned lazy image with a 3:2 crop, and one gold detail link with a room-specific accessible name. Text heights are natural; flex layout aligns the price/action area within each grid row. It makes no booking, occupancy, size, tax or inclusion claims. The style sample renders all three tiers through CatalogueGrid.

`CatalogueGrid` provides a plain layout wrapper for cards/tiles: one column below 768px, two from 768px and three from 1024px, with `gap-6` and stretched items. It owns no outer container or section spacing. Children should use `min-w-0` and allow text wrapping; no fixed text heights are needed. The development style sample includes three RoomCards. The wrapper has no landmark or list semantics; compose semantic articles or a labelled section as appropriate.

`StoryMosaic` takes typed `items` with stable IDs, titles, paragraph arrays, image metadata and optional internal actions. Rows alternate image/text positions from the tablet breakpoint; the DOM stays image-first for a consistent mobile reading order. Images have intrinsic dimensions and a 4:3 mobile crop; desktop images fill their row height while text remains content-driven. Pass `headingLevel="h3"` when nesting under an H2 (the default is H2). Each row has an instance-unique heading ID. A labelled `image: { placeholder }` is available for development when assets are missing; replace all placeholders with `{ src, alt, width, height }` before launch. Use empty alt text only for decorative images. Empty item arrays render nothing. The style sample demonstrates short/long copy, an omitted action and user-supplied double-room/Royal Suburbs images for development review. Production asset approval is separate. See `docs/validation/e04-t01/README.md` for evidence and limits.

`PageTitleBand` provides the page's single H1, optional description and optional breadcrumbs on a full-width ivory band. Supply ancestor `{ label, to }` entries; the current page is appended as non-link text with `aria-current="page"`, using `currentLabel` or the title. Omit breadcrumbs for a title-only band. Mark a route with `handle: { fullWidth: true }` to let its page own section containers and vertical spacing; other routes retain the existing main container. Put one `site-container` inside each full-width section. The style sample demonstrates this opt-in without changing product pages or route-focus behaviour.

`SectionHeading` renders a required `title`, optional paragraph `eyebrow` and `description`, and an optional `id` on the heading for a parent section's `aria-labelledby`. It defaults to a centred `h2`; use `as="h3"` for nested sections and `align="left"` for stories. Descriptions use the shared prose width. The parent owns section spacing and any actions; omitted content leaves no empty elements. Short/long examples live on `/__style-sample`.

`ActionLink` reuses the gold action style: pass `to` for React Router navigation or `href` for ordinary anchors (external URLs, fragments, phone or email). The typed props exclude supplying both. `ActionButton` accepts native button props and defaults to `type="button"` to prevent accidental form submission; pass `type="submit"` explicitly when needed. Both preserve native props/refs and caller classes through `cn`. At the user's request, actions use a deeper-gold keyboard focus colour instead of a ring, deeper-gold hover with a 1px lift, and a darker pressed state. Reduced motion disables movement; forced colours uses a system highlight for focus. Use native `disabled` on buttons; links have no disabled API. Examples, including long labels and light/navy surfaces, live on `/__style-sample`. Existing navigation components are unchanged.

`SiteFooter` is mounted in `SiteLayout`. It consumes shared business/footer navigation data, with labelled navigation regions and exact current-page links. Validation evidence is in `docs/validation/e03-t04/README.md`. The temporary development index and style-sample link live separately in a collapsed, development-only tools area below the footer and are excluded from production JavaScript.

`RouteTransitions` coordinates focus with React Router scroll restoration. New pages focus their H1/main, fragments focus their target, query-only updates preserve position/focus, and history entries restore separate scroll positions. It must remain the only scroll-restoration owner. See the layout notes and E03-T04 evidence before adding competing scroll/focus effects to page components.

For new interactive components, consider the installed shadcn/ui setup before implementing complex behaviour yourself. Add only needed primitives under `src/components/ui`, keep the Dorchester styles, and verify keyboard/focus behaviour. See [setup and component guidance](../../docs/SHADCN_UI.md) and the root `AGENTS.md`. Existing header/mobile navigation stays in place.

`SiteHeader` owns the branded header and navigation landmarks, rendered by `SiteLayout` on every routed page. It uses the provided crest, logo-navy background, light navigation and gold booking action from shared navigation data. Desktop navigation starts at 1024px; the property-name text appears from 1280px beside the crest (and at tablet widths).

`DesktopNavigation` renders ordinary links and disclosure buttons, not application-menu roles. Following the user's reference-style refinement, each group label is its disclosure button, with its overview link inside the panel; separate arrow controls are removed. It exposes expanded state and panel IDs, keeps one panel open, and closes on Escape (returning trigger focus), outside pointer interaction, focus leaving a group and crossing the mobile breakpoint. `SiteHeader` keys this component to the router location key so navigation/history resets all disclosure state.

On hover-capable devices, mouse entry opens a desktop group and leaving its trigger/panel closes it. Keyboard-visible focus within the group keeps its links available until focus leaves or Escape is pressed. A mouse click following hover keeps the panel open; keyboard and touch activation toggle it. Mobile navigation remains tap/disclosure based.

Rooms and Services have direct overview links in both headers. Desktop hovering opens their detail dropdowns; alternative desktop keyboard/touch access remains explicitly deferred. On mobile, the user approved separate plus/minus buttons in `MobileNavigationGroup`, with 44px targets, expanded state, controlled panel IDs and direct parent links. Children collapse independently and reset when the menu contents unmount. The centred labels remain aligned when the controls appear. Our bar and Discover retain their native mobile disclosures. All 17 destinations are now present in the mobile menu. Full mobile focus/responsive validation remains part of E03-T03.

Both desktop and mobile navigation use `src/app/navigation.ts` to highlight parent sections in gold. Desktop top-level items use regular 14px type with tracking and a short gold bar flush with the bottom of the 80px header. Exact `NavLink` destinations alone receive `aria-current="page"`; the helper matches catalogued destinations and single-segment article routes, not broad room/service prefixes. Overview links are not declared current on detail pages. Mobile links retain exact-page underlines, with no visible subgroup arrows. The booking CTA also underlines on its exact route.

`MobileNavigation` provides the reference-style centred dropdown below the mobile header. The hamburger becomes a cross when open; all groups, secondary links and the booking CTA reuse shared navigation data. The non-modal panel supports Escape/focus return, outside dismissal, close-on-navigation, native subgroup disclosures and scrolling on short screens. Desktop breakpoint changes reset the panel. See `docs/validation/e03-t03/README.md` for checks and screenshots.

Mobile route-key changes permanently clear open state so Back/Forward cannot revive a menu opened on an earlier history entry. Preserve this reset when changing state handling; a visibility check against the current route key alone is insufficient.

`DevelopmentNavigation` is a temporary review index for all 17 required destinations, rendered in the development-only tools area. It uses router links with exact active-page matching and the shared destination list from `src/content/navigation.ts`. It contains no property facts or API calls and is not part of the public footer.

`SetupCheck.tsx` is a temporary TypeScript, alias and Tailwind demonstration. Keep it until the routing layout replaces the starter screen.
